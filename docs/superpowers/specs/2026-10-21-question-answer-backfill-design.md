# One-Time Question Answer Backfill Design

## Goal

Generate proposed correct option IDs once for the 51 unanswered objective questions, persist them in the repository's question data, and serve them from the static bank without calling an LLM while the app loads.

## Current state

- The production app is static and has no persistent database. Its question bank is assembled during `npm run prepare:data` and bundled for the browser.
- The existing `/api/quiz-coach` route is intended for local Vite development and is not included in production.
- The current bank has 1,795 questions: 51 objective questions have no answer key (44 single choice and 7 multiple choice); 551 essays intentionally use reference answers and rubric grading and must remain unchanged.

## Design

1. Add a one-time server-side Node script that reads `OPENAI_API_KEY` and `OPENAI_MODEL` from the repository-root `.env` or environment. It sends only the 51 unanswered non-essay questions, their choices, and available source evidence to the configured model. It does not run from the browser or during build/page load.
2. Require structured output containing each question ID, proposed option IDs, a short Vietnamese explanation, and a confidence value. Validate that every response ID is in the target set, each option ID exists on that question, and answer cardinality is valid for single-choice questions. Abort and write nothing if any item is missing or invalid. Do not overwrite an answer added since target selection.
3. Persist successful results as a tracked overlay at `web/content/answer-key-backfill.json`. The build-time question-bank builder merges this overlay into its generated bank. All populated answers remain `answer_proposed`, with reviewer notes that they were generated by a one-time model backfill and are not expert verified.
4. The browser consumes the built question bank as it does today. It makes no LLM request to populate answer keys. Re-running the command skips already-filled questions; it can only generate for still-missing target IDs.

## Boundaries

- Do not fill the 551 essay `correctAnswers` fields. Their explanations/reference responses and rubric grading remain the source of truth.
- Do not silently mark model proposals as verified or change scoring eligibility.
- Keep the model key server-side; never add it to a `VITE_*` variable, generated JSON, logs, or commits.
- Preserve any model response and provenance only in the overlay's answer/explanation metadata; omit secret data and full prompts.

## Acceptance criteria

- Backfill invocation targets only unanswered objective questions.
- Invalid, incomplete, duplicate, or out-of-question option IDs are rejected before the overlay is written.
- Successful results are persisted in repository data and merged into the generated bank at build time.
- Page loads and ordinary quiz navigation do not call the LLM.
- Essay questions remain untouched; generated answer status remains `answer_proposed`.
